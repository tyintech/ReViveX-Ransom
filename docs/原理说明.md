# ReViveX Ransom 恢复原理

[English](PRINCIPLES.en.md) · [返回 README](../README.md) · [技术说明](技术说明.md)

本文说明“自动恢复”为什么能从被勒索病毒加密的 Hyper-V 虚拟磁盘（VHDX）中按原名找回文件。使用方法见 README。

## 1. 为什么文件还能找回

- 这类勒索病毒为了加快速度，对大文件只加密几段（例如文件头、中段、尾段，各占约 1%），其余大部分数据仍是明文。
- VHDX 的文件头、区域表和**块映射表（BAT）**都在文件开头，正好落在被加密的区域里。块映射表记录“虚拟磁盘的第几块数据存放在 VHDX 文件的什么位置”，它丢失后，普通工具就打不开、也挂载不了这个磁盘。
- 但虚拟机里 NTFS 文件系统自己的记录——文件记录（MFT FILE 记录，含文件名、大小、数据位置）和目录索引（INDX 块，含目录下的文件名）——大多还在明文区。
- 只要能把丢失的块映射表重新算出来，就能沿着 NTFS 记录把文件按原名、原目录读出来。

## 2. 恢复步骤与原理

**① 只读诊断与抽样。** 检查文件头签名和勒索尾标，按尾标推算可能被加密的区间；在明文区抽样读取，确认 NTFS 记录是否幸存。全程只读，不改动源文件。

**② 证据扫描。** 顺序读一遍整个文件，只保留很小的“证据”：NTFS 文件记录、目录索引块、常见文件格式的开头特征（如 JPEG、PDF、ZIP 的文件头）、全零区域等。证据只有源文件的极小一部分，后续步骤都基于证据计算，不再反复读源盘。

**③ 重建块映射。**
- 目录索引块里写着它属于哪个目录，而该目录的 NTFS 记录又写着这个索引块在卷内的位置。两者对照，就得到“卷内位置 ↔ 文件实际位置”的**精确锚点**。
- VHDX 的数据块在文件中按 1 MiB 对齐。不同分区的锚点有各自固定的偏移规律，因此能自动分出有几个卷、每个卷的分区偏移、簇大小和块大小，无需人工填写。
- 没有锚点的块，用前后锚点推算候选位置，再用“这里应当是某个文件开头”的特征核对（例如记录显示某 PDF 从这里开始，那么这个位置就应该是 `%PDF`）。推算方法会先在已知块上测试准确率，测试完全正确的距离范围内才采用。
- 块大小宁可估小、不可估大：估小只是少用一些证据，估大会把整块映射到错误位置。

**④ 区分卷与镜像。** 虚拟机的数据盘里常存放其他磁盘镜像或备份文件（.vhdx、.bak 等），它们内部也有 NTFS 记录，会混进证据。程序按每段 MFT 的文件头吻合率判断：本卷的记录吻合率接近 100%，镜像内的记录接近 0%，据此排除，避免文件名和路径张冠李戴。

**⑤ 缺块匹配。** 对仍然缺少位置的块，只用能逐字节核对的证据寻找：ZIP 成员的 CRC 校验、PNG 分块校验、PDF 对象编号、多个文件头同时吻合。只有“所有证据全部吻合、且只有一个候选吻合”才接受，平局一律放弃。匹配规则先在已知块上自检，自检出现一次误判就停用。候选位置按磁盘顺序一次读完，避免慢速硬盘的随机读取。

**⑥ 按原名写出。** 只有文件用到的每一块都有可信证据时才写出。路径逐级向上查找父目录，父目录的记录序号必须一致且确实是目录，否则放到“上级目录名丢失”文件夹，不借用错误的目录名。写出采用排他创建，从不覆盖已有文件。

**⑦ 已删除文件。** NTFS 删除文件时只把记录标记为“未使用”，数据通常还在。程序找出这类记录：如果它的数据位置没有被现存文件占用，就单独恢复到“已删除文件”目录；已被占用的则列为无法恢复。

**⑧ 分级与整理。** 写出的文件逐个做格式结构检查（如 JPEG 扫描整段压缩数据、PNG/ZIP 核对校验和、PDF 核对对象位置、数据库做完整性检查），分为可用 / 待确认 / 疑似损坏，Windows 缩略图缓存单独存放。整理只移动、不删除，每次移动都有记录，可以撤回。

## 3. 可靠性与安全

- **只读：** 源文件只读打开（Windows 上同时阻止其他程序写入），每次读取都限定大小，适用于十几 TB 的文件。
- **可中断：** 每个步骤都有检查点，取消、断电或程序被关闭后可以从中断处继续，不会重复写出文件。
- **不夸大：** “写出”不等于“恢复成功”。分级只说明文件结构完整，不能证明内容与原件完全一致；落在加密区内的数据和记录无法恢复。
